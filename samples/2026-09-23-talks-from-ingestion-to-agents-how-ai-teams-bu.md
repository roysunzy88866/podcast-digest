# 智能体时代，你的 PDF 数据管道拖后腿了吗

<div class="pd-byl"><b>Adit Abraham</b> · Reducto 联合创始人兼 CEO · 2026-09-29</div>

这一集是 [[Reducto|Reducto]] 联合创始人兼 CEO Deet 的一场 20 分钟演讲。Reducto 是一家做「[[智能体|智能体]]文档处理平台」的公司，客户包括 Harvey、Lagora、Rogo 等 AI 原生公司，也有全球最大的金融机构和保险公司——这些机构手里有几十年的历史数据，全都锁在 [[PDF|PDF]]、扫描件、电子表格这些非结构化格式里。

到目前为止，Reducto 已经为客户处理了数十亿份文档。他的核心观点：智能体应用正从「信息综合」走向「真正干活」，这让数据质量从一个次要问题变成了整个流水线的命门 <button class="pd-ts" data-t="02:59" data-who="Deet" data-en="I'll start with the first thing, which is something that I assume has been harped on a lot. If you went to AI Engineer a few years ago, the word that you would have heard in every single talk would have been RAG, and everybody was building some form of RAG application." aria-label="回原文"></button>。

## 从 RAG 到智能体：坏输入的风险被放大了

几年前大家都在做 [[RAG|RAG]](从资料库里检索出相关内容再让模型回答)，应用本质上就是信息综合：企业搜索、问答机器人。今天的关键词换成了智能体——让模型端到端地完成白领工作，不只是从 PDF 里回答问题，还要生成和修改 PDF <button class="pd-ts" data-t="03:47" data-who="Deet" data-en="And that same sort of shift is starting to happen for all sorts of white-collar work. Whether you're in finance or insurance or healthcare, people are starting to make autonomous decisions." aria-label="回原文"></button>。

这个转变把数据问题的代价放大了。问答答错了就错了；而当智能体在一批文件上做出多个**会累积复合的决策**、还要拉取多个数据源时，一个坏输入会沿着流水线扩散成系统性风险 <button class="pd-ts" data-t="04:19" data-who="Deet" data-en="And the common core for all of this is it actually ends up being an even more importance problem to solve for when you start having these multi-step pipelines. If you're just doing question and answer, there is obviously a risk that comes with just answering the question." aria-label="回原文"></button>。而对很多企业来说，数据天生就是非结构化、分散、多模态的：团队随手把文件丢进 Google Drive、Box,你甚至不知道自己的语料库里到底有什么。

## PDF 为什么至今仍然难

PDF 难，是因为这个格式非常老，而且是为一个完全不同的场景设计的——忠实呈现并打印文档。Deet 见过 1990 年代初给打印机写 PDF 驱动的人。

而今天我们想要的是 markdown 式的表示，让智能体能拿来推理。更麻烦的是，人类用视觉编码了大量信息：没有干净网格线的表格、合并单元格、折线图、连人都不好认的手写体——这才是真实语料的长尾 <button class="pd-ts" data-t="06:45" data-who="Deet" data-en="And in the real world, humans encode so much context visually. The average financial analyst that is a new grad in their IB role is not going through and thinking in terms of will agents consume this deck." aria-label="回原文"></button>。

有个 benchmark 很能说明问题：数据实验室 Surge 的 GDPPDF 基准，专门测模型能否通读 PDF 并基于内容做判断，连当前最前沿的模型 Fable 也只有约 30% 的成绩 <button class="pd-ts" data-t="05:43" data-who="Deet" data-en="I don't know if any of you follow Surge which is a data lab that works with a lot of the foundation model companies. They have this really great benchmark called GDPPDF where even Fable, like current frontier of model intelligence, is at about 30% on their benchmark." aria-label="回原文"></button>。

## 传统 CV 与 VLM 各有其位

[[VLM|VLM]](视觉语言模型，能同时「看懂」图像和文字的模型)本质上是横向通用的，第一次让「像人一样读文档」成为可能，尤其擅长手写体这类传统 [[OCR|OCR]] 从来搞不定的东西。但它不是万能方案：规模化处理数亿份文档时，你还要确定性、效率这些次要考量 <button class="pd-ts" data-t="08:13" data-who="Deet" data-en="And so we found that they were incredible for all sorts of things like handwritten text in a way that traditional OCR just never was. But the flip side is that we don't think that they're a one size fits all solution." aria-label="回原文"></button>。

他的关键做法是**分解问题**：得益于自动驾驶研究的进步，目标检测这类传统 CV 技术已经比十年前成熟很多，**低于一亿参数的小模型就能很好地检测文档版面**，还能跑在 CPU 上、大规模运行，让你在区域层面就知道哪些部分难处理 <button class="pd-ts" data-t="08:43" data-who="Deet" data-en="As autonomous vehicle research has gotten better, techniques like object detection are more sophisticated than they were a decade ago. And so we find that sub 100 million parameter models are really effective for things like detecting the layout of a document." aria-label="回原文"></button>。VLM 则用来补语义——识别并纠正流水线中容易犯的错误。

## 智能体 OCR:验证与修正层

由此他提出「agentic OCR」的概念，类比人在回路：先走一遍 CV + VLM 的解析，再加一层**验证与修正**，产出高置信度的结果 <button class="pd-ts" data-t="10:29" data-who="Deet" data-en="And that's a question of how do we actually represent what a human would have seen if they had read that document. So the way that we see this is agentic OCR is almost like that human in the loop analogy where you have the first inputs go through with a CV plus VLM parse, but then you have a verification and correction layer that ends up leading to a high confidence output." aria-label="回原文"></button>。

为什么不能直接「把 OCR 扔给 Gemini、写个漂亮提示词」？因为他们发现，做下一 token 预测式的改写会引入全新的失败案例：太聪明的模型会开始「好心修正」，反而不忠实于原文——比如看到 total 这个词，如果人类在那个表格里算错了，模型有时会自己把数值重新加一遍 <button class="pd-ts" data-t="10:06" data-who="Deet" data-en="You can apply similar sort of principle here that is not just sending OCR to Gemini, writing a really pretty prompt, asking it nicely to not deviate too much from the original because we find that when you're doing that sort of next token prediction, you introduce net new loss cases where models that are really intelligent will start actually correcting things not faithfully to what was in the document." aria-label="回原文"></button>。你真正想要的是 token 级别的精准修正：句号错成逗号、零错成字母 O,这些细节在财务场景里极其要命。

## 表格、embedding 与检索：为消费者格式化数据

解析之外还有编排问题。简单表格用 markdown 表示就够了；但合并单元格承载大量语义的复杂表格，markdown 会丢信息——用 HTML 表示，LLM 推理得很好，却浪费大量 token、成本很快上去。所以这是一个动态选择：简单表格走 markdown,复杂表格走 HTML <button class="pd-ts" data-t="11:39" data-who="Deet" data-en="And obviously on the other end of the spectrum, you probably don't want to go through and encode simple tables in HTML, because then you have a lot of HTML tags that are erroneous." aria-label="回原文"></button>。

但别只考虑语言模型。如果你还要做 embedding(把文本转成向量以便检索)，麻烦来了：真实用户不会把表格数值一一念出来，只会问「收入随时间怎么变化」并假定你检索得到正确的表。

而 embedding 模型很难把这种自然语言提问和一大坨 HTML 标签加数字关联起来 <button class="pd-ts" data-t="12:35" data-who="Deet" data-en="And they assume that you're going to retrieve the right table when it's relevant. And whereas language models can reason through that text effectively, if you're pulling from a large corpus, we find that embedding models really struggle to correlate that natural language human prompt with this messy blob of HTML tags and numbers." aria-label="回原文"></button>。解法几乎不费力气：**为同一张表额外生成一份自然语言表示**——推理时喂 HTML,检索时用自然语言块，两全其美。

更好的输入直接提升最终输出。用同一个 GDPPDF 基准测试，同时给模型原始 PDF 和结构化解析结果，无论 Gemini、Anthropic 还是 OpenAI 的模型，端到端性能都提升；而且不止准确率——模型花在「理解数据」上的推理 token 变少、延迟降低，GPT 5.5 和 Opus 加上好的输入后，开箱即用就能胜过 Fable <button class="pd-ts" data-t="14:05" data-who="Deet" data-en="So what we found is that if you take the same exact benchmark that I mentioned earlier, unfortunately we couldn't test it on Fable because our access was cut, but if you test on other models and you give it both the original PDF but also a structured representation of the PDF, like the parse results here, across models, whether it's Gemini, whether it's Anthropic, or OpenAI, you find that you actually improve end LLM performance just from better inputs." aria-label="回原文"></button>。

## 分类与切分：被低估的编排手段

另一个被严重低估的手段是分类和切分。无脑塞满上下文，除了 token 成本，质量本身也会被侵蚀。

把正确的文档路由到合适的流水线、只传入真正相关的片段，能带来很大提升空间 <button class="pd-ts" data-t="15:30" data-who="Deet" data-en="As a result of passing in too much. And instead what we find is you can get a lot of headroom by thinking through things like how do you classify the right documents to the right sort of pipeline?" aria-label="回原文"></button>。他们的真实用例：几百页的纸质邮件包，内容还被人交错在一起——让模型自己理顺这些，是对你真正想做的任务(提取、推理、决策)的干扰。

## 智能体工具框架：攻克折线图与召回率

Deet 认为最令人兴奋的前沿是 agent harness(给智能体配上一整套工具让它自主迭代)。例子一：折线图。

他和全球最大的对冲基金合作，折线图编码了巨大的数据表，像素级细节靠传统视觉编码器必丢——没有任何模型能单次搞定。唯一可行的方法是给智能体配代码解释器、让它能把自己生成的图表可视化，然后一次又一次发现折线图中的错误并迭代，最终重建出完整的 markdown 数据表 <button class="pd-ts" data-t="17:37" data-who="Deet" data-en="And the only way that we were able to get there was to have an agent with all sorts of tools. It has its own code interpreter, it has the ability to visualize the chart that it's generating, and it's iteratively going through, it's finding mistakes in the line chart again and again and again until it's able to get to the final output." aria-label="回原文"></button>。

例子二：结构化提取。像有几万个字段的 CBP 表单，问题往往是**隐蔽的**——悄悄丢行、丢内容。

今早 MicroOne 发布的基准揭示了市场的分化：带最大推理的前沿模型精确度极高(提取出的行大概率不是幻觉)，但**[[召回率|召回率]]非常挣扎**，悄悄丢掉很多内容；反过来，专门的文档处理服务精确度落后但召回更好。只有用[[harness|智能体工具框架]]——父智能体为子智能体设定验证标准——才能同时拿到精确率和召回率的局部最优 <button class="pd-ts" data-t="18:49" data-who="Deet" data-en="On the flip side, a lot of dedicated document processing services are actually behind Frontier models from a precision perspective but close that gap on a recall perspective." aria-label="回原文"></button>。

## 评估要贯穿每一步

他认为全场最重要的一点：**[[评估|评估]](evals)应该支撑你所有的决策**。既要有现成数据集的评测，也要有实时生产监控——因为生产数据和人为构造的数据集一定不同 <button class="pd-ts" data-t="19:13" data-who="Deet" data-en="The last thing and maybe the most important thing from this talk is that I think at the end of the day evals should underpin all of your decisions and it's been a big part of how we think about our product." aria-label="回原文"></button>。

而且别把评估只当宏观视角，最好的团队对流水线**每一步**都做细粒度评估：解析层的输入好不好、检索管道对不对、末端格式化有没有问题，最终落点是——你能否提升端到端智能体的性能？解析完美但检索糟糕，一样白搭。

## 下一站：给智能体一个文件系统

随着智能体变强，你可以放弃几年前那种确定性流水线。Reducto 做了一个 CLI:不再让文档遵循固定流程，而是给智能体建一个可遍历的文件系统，让它自己决定读什么、用什么工具 <button class="pd-ts" data-t="20:18" data-who="Deet" data-en="The most important thing, I think, is as agents get better and better, you can deviate from the sort of deterministic pipeline that you would have had a few years ago." aria-label="回原文"></button>。

文档被拆成两部分：按需读取的内容字段，加上做引用等场景需要的元数据(如边界框)。接下来几个月，他们会往文档生成方向走得更远。

## 本集带走

- **把解析问题分解开**：为合适的任务用合适的工具——小参数 CV 模型管版面检测(还能跑 CPU),VLM 管语义与手写体，才能同时逼近准确率、成本、延迟的前沿。
- **警惕模型的「好心修正」**：别指望一个提示词让大模型忠实转写，它会把表格算错的地方自己加回去；用 token 级验证修正层，句号/逗号、零/O 这种细节才保得住。
- **为数据的消费者格式化**：复杂表格给 LLM 用 HTML、给 embedding 用同一张表的自然语言表示——几乎零成本，却直接提升检索命中和最终答案质量。
- **别忽视编排**：[[分类与切分|分类与切分]](把对的文档送进对的管道、只传相关片段)是被低估的质量杠杆，别让模型浪费时间理几百页交错的纸质邮件。
- **隐蔽丢行要靠智能体工具框架解**：前沿模型精确但召回差，专门服务相反；父智能体设验证标准、子智能体执行，才能两头兼顾。
- **每个阶段都做评估**：解析、检索、格式化、端到端，一层层测；并且要监控真实生产数据，别只信构造数据集。

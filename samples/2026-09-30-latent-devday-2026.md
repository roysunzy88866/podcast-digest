## 计算机使用到底哪里变了

Ari 的职业生涯一直做自动化：Apple 的 Shortcuts、创业公司 Sky，再到现在 OpenAI。他总结驱动他的主线很简单：帮人省掉运营性事务的时间，去做更重要的事 <button class="pd-ts" data-t="06:06" data-who="Ari" data-en="On the through line, I guess I've always been excited about automation and helping people automate tasks because then you can save time in your life and focus on things" aria-label="回原文"></button>。

回头看，他看到的最大变化是模型行为模式的转变：「以前它们可以比较可靠地开始任务，但之后就会遇到问题。而现在它们非常擅长调试——很擅长重试、内省哪里没有在正常工作」<button class="pd-ts" data-t="06:50" data-who="Ari" data-en="just in the I think the biggest delta that I see is before they could like reliably start tasks, but then they would run into problems. And now they're really good at debugging." aria-label="回原文"></button>。

另一条关键路线是引入更多模态。过去计算机使用产品的典型循环是：截图 → 尝试操作 → 「我得往下滚到下一页」→ 再截图 → 再操作，大量时间耗在翻页上。现在模型可以按任务选择机制：截图、可访问性接口（accessibility，为视障用户提供的界面结构化描述），或者 playwright（一个能直接操作浏览器的自动化工具），不再只靠截图硬滚 <button class="pd-ts" data-t="09:39" data-who="Ari" data-en="One more specific example of that is in the past, I think we saw a lot of computer use products had to spend a lot of time scrolling. So it would take a screenshot." aria-label="回原文"></button><button class="pd-ts" data-t="07:33" data-who="Ari" data-en="multi-modal interfaces. The model may use screenshots, it may use accessibility, it may use playwright. It can use a lot of different mechanisms based on the task at hand." aria-label="回原文"></button>。

一个容易被低估的功能是 AppShot：在 [[Codex|Codex]] 里连按两下 command，把当前应用的内容抓进对话。它看起来像截图，实际不是——截图不包含链接指向哪里、日历里被截断的标题；AppShot 给模型的是完整上下文，包括原始文本和无障碍表示。

Ari 透露有个极客玩法：点开附件右上角的小按钮，就能看到原始的无障碍表示。团队为此投入了大量精力让它既完整又 token 高效，「这里面有点像一门艺术」<button class="pd-ts" data-t="10:44" data-who="Ari" data-en="If you want to be really nerdy about it, you can go into Codex, take an app shot by hitting the two command keys. So you grab the content from whatever app you're working with," aria-label="回原文"></button><button class="pd-ts" data-t="11:42" data-who="Ari" data-en="Yeah, exactly. If you take a screenshot of a webpage that has a link, The screenshot doesn't include where the link goes." aria-label="回原文"></button>。有趣的是，这项为有障碍需求的人类发明的技术，成了喂给模型的最佳表示 <button class="pd-ts" data-t="11:12" data-who="Ari" data-en="And, you know, it turns out that the same technology that was invented for humans, you know, who maybe have accessibility needs." aria-label="回原文"></button>。

## 让智能体自己测自己写的软件

Ari 最喜欢、实际中也很常见的用例：让智能体测试它自己构建的软件。传统流程里，Codex 帮你写完代码后，你就成了智能体的 QA；有了计算机使用，智能体可以构建、然后自己操作界面测试，补全整个软件开发生命周期，「等它到我手上的时候，它已经能正常工作了」<button class="pd-ts" data-t="18:16" data-who="Ari" data-en="Test it. And you are now like QA for the agent, right? So with computer use," aria-label="回原文"></button><button class="pd-ts" data-t="18:30" data-who="Ari" data-en="So I have a lot of fun, you know, building stuff, having the agent test it. By the time it comes to me, it's already working. I have extra fun because sometimes I'm like developing computer use itself." aria-label="回原文"></button>。

Ari 还自嘲有额外的乐趣：他在开发 computer use 本身，所以现在有「一个 computer use 智能体在用我的 computer use 智能体，而那个又在用别的东西」<button class="pd-ts" data-t="18:36" data-who="Ari" data-en="I have extra fun because sometimes I'm like developing computer use itself. And so now I have a computer use agent that's using my computer use agent that's using something else." aria-label="回原文"></button>。主持人的实践是用计算机使用逐屏克隆一个体验很差的 SaaS——截屏、记录、让 Codex 复刻。

## 瓶颈在哪：等页面加载

关于下一步，Ari 判断下一个前沿是「lowercase」（小写水平的延迟），一旦达到，就能做出真正实时的产品，并大幅降低使用计算机使用的激活能量 <button class="pd-ts" data-t="12:47" data-who="Ari" data-en="the average human, probably in most cases. And I think that the next frontier is to have computer use be like lowercase. I think that'll be really consequential and exciting when that happens" aria-label="回原文"></button>。现在的小瓶颈分布在模型、[[推理|推理]]、[[harness|harness]]（模型外围的执行框架）和表示各层。

一个非常具体的瓶颈：「随着计算机使用变得更快，我们越来越多地被单纯执行一个操作的速度所瓶颈化」——比如写一个 wait 然后执行这个 wait。理想状态是事件驱动（页面加载完成这类信号直接触发下一步），浏览器导航有加载事件，但很多场景做不到，比如和客服聊天：回复可能 30 秒，也可能三分钟 <button class="pd-ts" data-t="13:45" data-who="Ari" data-en="there's things on the harness side, there's things in the representation. We find that as computer use gets faster, we're increasingly bottlenecked by just the speed of doing an operation." aria-label="回原文"></button><button class="pd-ts" data-t="14:22" data-who="Ari" data-en="Like an event-driven way maybe to do that. When possible, you want it to be event-driven. The web browser has load events for web navigation," aria-label="回原文"></button>。

## 给开发者的建议

计算机使用这次进入了[[智能体 API|智能体 API]]，开发者可以用 Codex 和 ChatGPT 同款实现来构建。Ari 的核心建议：自己造 harness 有很棒的工作可做但很难，而且「我们是在自己的计算机使用框架上训练我们的模型，所以使用模型分布内的那一套是有优势的」——可能带来速度、成本和准确率上的好处 <button class="pd-ts" data-t="16:31" data-who="Ari" data-en="And also, we train our models on our computer use harness, so there is an advantage to using the one that's in distribution for the model." aria-label="回原文"></button>。信任层面，他的原则是：构建可靠的东西、加上正确的安全检查、在做有重大后果的操作（比如付款）前征得用户同意、按应用场景限制可访问的网站 <button class="pd-ts" data-t="17:02" data-who="Ari" data-en="And so I think it's incumbent on us to sort of build that trust over time by making sure we're building By building things that are reliable, by building the right kinds of safety checks," aria-label="回原文"></button>。

## 后半场：API 侧的新东西

Nick Winch 领导 API 团队产品，加入 OpenAI 约三年，一直负责模型发布。GPT-6 带来的核心新能力是异步工具调用：「工具调用耗时太长，以至于你不必在工具运行时暂停模型的执行」——可以发起调用、继续推理，再回来查看。配套的 WebSockets（长连接双向通信）则在 Codex Spark 时首次推出，专门用来降低工具来回交互的开销 <button class="pd-ts" data-t="20:16" data-who="Nick Winch" data-en="A lot of the things that you're seeing in Codex And everything is that tool calls take so long that you don't have to like pause the models execution while the tool is running." aria-label="回原文"></button><button class="pd-ts" data-t="22:34" data-who="Nick Winch" data-en="And yeah, WebSockets. Actually, it was like the first time we launched WebSockets," aria-label="回原文"></button>。

UltraFast（首次进入 API 的极速模式）背后是推理团队的转变：前几个月他们聚焦效率和降本——「这就是我们能把 Luna 的价格砍掉 80% 的原因」，现在换挡到把速度做到极致 <button class="pd-ts" data-t="22:09" data-who="Nick Winch" data-en="at least for a couple of months, a lot of it was focused on efficiency and driving the cost down, which is how we were able to cut the Luna price by 80%." aria-label="回原文"></button>。

[[Decisions API|Decisions API]]（超快的分类/决策模型 API）的来历颇具 OpenAI 风格：Jev 发布后，一个推理团队的人和一个基础设施团队的人觉得「这太棒了，我们要拿它来捣鼓一下」，做出能用的原型，现在在做延迟爬山优化。Nick 明确说了实现方式：「我们没有为此训练新模型，完全是构建在已有的同一套 Luna 权重之上」——用结构化输出做约束、极致优化推理栈的 TTFT（首 token 延迟）、多问题并行批量运行，第一版就是零样本。相比无视觉能力的竞品，Luna 的视觉能力是免费送的 <button class="pd-ts" data-t="24:53" data-who="Nick Winch" data-en="And so a guy from inference, this one awesome guy from The infra team are like, this is amazing. We're going to like hack on it." aria-label="回原文"></button><button class="pd-ts" data-t="27:38" data-who="Nick Winch" data-en="Yeah, totally. So we haven't trained a new model for this. We're building this purely on top of the same Luna weights that we have." aria-label="回原文"></button><button class="pd-ts" data-t="28:43" data-who="Nick Winch" data-en="Yeah, yeah, yeah. Like we get it for free with Luna. Yeah." aria-label="回原文"></button>。

用例上，内部最明显的是用户运营团队给支持工单分类；Nick 最期待的原型是把 Decisions API 接到 GPT Live（双向实时语音 API，采用「思考者-说话者」架构，快的前端模型负责说话、Astra 坐镇后端）上——过去 GPT Live 的工具调用一直感觉慢，接上 Decisions API 后控制电脑「感觉起来快得多、自然得多」<button class="pd-ts" data-t="30:47" data-who="Nick Winch" data-en="Decisions API, use cases internally have been pretty obvious. The user ops team was jumping on it. We were like, we were going to classify all of our support tickets." aria-label="回原文"></button><button class="pd-ts" data-t="26:21" data-who="Nick Winch" data-en="So GPD Live is this like... Thinker talker. Super fast, yeah, thinker talker thing." aria-label="回原文"></button><button class="pd-ts" data-t="26:42" data-who="Nick Winch" data-en="of GPD Live controlling a computer. It just feels so much more snappy and natural. So I'm kind of excited to see what people do with Live and with Luna on Decisions API." aria-label="回原文"></button>。

## 性能：缓存与压缩

[[Responses API|Responses API]]（主力 API）的两大方向是延迟和[[缓存|缓存]]。缓存针对个人智能体这类单线程长跑场景：多付一点缓存费，保证更长时段的缓存读取——「你三四个小时后再回来，仍然能拿到缓存性能」；还有预热功能，提前支付缓存写入费，之后 30 分钟内随时可用，还能派生大量线程实例 <button class="pd-ts" data-t="33:53" data-who="Nick Winch" data-en="And we guarantee cache reads for a much longer period. So even if your instinct thread, for example," aria-label="回原文"></button><button class="pd-ts" data-t="34:32" data-who="Nick Winch" data-en="So the caching part is really important. Yeah, I also want to talk about pre-warming. We have that in the API now." aria-label="回原文"></button><button class="pd-ts" data-t="34:49" data-who="Nick Winch" data-en="and then have it ready to go for the next 30 minutes for whenever. And it can spawn many instances of that thread. Exactly, yeah." aria-label="回原文"></button>。

上下文总会撞天花板，[[压缩|压缩]]（compaction，把长对话历史浓缩以省 token）的最佳实践：智能体 API 里内置于 harness；Responses API 有服务端压缩——设一个 token 阈值，到了自动压缩；而很多大型编码智能体喜欢手动做，开源 Codex harness 用的就是 slash compact 命令。团队还在试验基于文件的新压缩技术，部分已实现在 Codex harness 里 <button class="pd-ts" data-t="35:45" data-who="Nick Winch" data-en="You decide for us, right? Yeah, exactly. So in the agency API, it comes built into the harness." aria-label="回原文"></button><button class="pd-ts" data-t="36:23" data-who="Nick Winch" data-en="Yeah, it is the manual way. And I don't know, but a lot of the big coding agents like to do it manually. I mean," aria-label="回原文"></button>。

最后是 Nick 留给行业的问题。他此前在 Stripe 做产品，Stripe 的玩法是在核心支付原语上构建更高层的产品；AI 里的对应问题是他反复思考的开放题：早期的 Assistants API 是一次不合适的尝试，现在的智能体 API 给了你 Codex harness，但「应该在其中给予多少灵活性才是合适的？

这是个开放性问题」<button class="pd-ts" data-t="37:14" data-who="Nick Winch" data-en="We're obviously very low level. I used to work at Stripe before this, and at Stripe," aria-label="回原文"></button><button class="pd-ts" data-t="37:38" data-who="Nick Winch" data-en="We had launched assistance API way back in the day and wasn't really the right fit. We were sort of going off with this agents API and it gives you the codex harness, but what's the right amount of flexibility to give in that?" aria-label="回原文"></button>。主持人的收尾类比：OpenAI 在做 AI 原生版的 AWS 发明——这是 EC2、这是 S3，每一个都是 AI 原生版本。

## 本集带走

- **写完代码让智能体自己测**：用计算机使用让智能体操作界面测试它刚构建的软件，把 QA 环节也自动化，等你验收时它已经能跑。
- **优先用官方 harness 而不是自造**：模型就是在官方计算机使用框架上训练的，用分布内实现可能同时拿到速度、成本、准确率的好处。
- **给模型「看结构」而非只给截图**：AppShot 式的无障碍表示包含链接指向、被截断文本等截图丢失的完整上下文，模型能做的事多得多。
- **长跑智能体的两个工程要点**：用长时效缓存（甚至预热线程、多实例派生）保证几小时后回来仍有缓存性能；上下文接近阈值时用服务端自动压缩或手动 compact 控制长度。
- **Decisions API 的定位**：超快分类/判断，不训练新模型，靠结构化输出约束 + 推理栈优化 + 并行批跑实现；适合工单分类、评测裁判、给实时语音模型补快速工具调用。

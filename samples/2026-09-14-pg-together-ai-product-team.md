# Together AI 产品团队全公开：一套仓库让 PM 下指令就出生产级 PR

这一集聊的是：一家 AI 公司的产品团队，怎么不靠「每个人各自用 AI 变快」，而是靠**一套共享仓库**让整个团队集体变快。

主角是 [[Together AI|Together AI]](为 AI 应用和[[智能体|智能体]]提供算力平台的初创公司，刚融资 8 亿美元)的产品团队——产品负责人 [[Charles|Charles]]、产品经理 [[Nicolina|Nicolina]] 和 Pavneet、开发者体验负责人 Hassan,在主持人 [[Akash|Akash]] 面前现场打开他们真实的仓库演示。

Charles 的出发点很直接：

当人人都能用智能体随手生成代码和文档，「过了一段时间之后，感觉新的派对失误就是把你同事的[[上下文|上下文]]塞满，我们全都开始互相扔垃圾内容」<button class="pd-ts" data-t="00:00" data-who="Charles" data-en="It felt like after a while that the new party foul was flooding your co-workers' context. We all just start launching slop at one another. What if we could put all these linings into one place?" aria-label="回原文"></button>。

每个人看着自己很高效，但这些产出的总和「并不必然是公司的前进」<button class="pd-ts" data-t="02:36" data-who="Charles" data-en="And it wasn't clear to me that the sum of all that was actually necessarily forward progress for us as a startup. And I imagine it's probably the same for a lot of other organizations." aria-label="回原文"></button>。

所以他们把 AI 的使用分成两层：**集中管理共享的上下文和[[技能|技能]]，个人自由发挥各自的工作流**。

## 仓库长什么样：一个 Markdown 目录 + 一堆技能

Nicolina 展示的「Together 产品仓库」主体是 Markdown 文件加少量 YAML。里面有两类东西：

**context(上下文)目录**：按产品分组(客户智能、[[沙箱|沙箱]]等)，还包括定期战略会议的成果——按使命划分的产品、季度里程碑。

写调研、和智能体一起写文档时按需拉取。

跨团队协作也靠它：「如果我在创建沙箱，而强化学习用户将会用到，我可以查看 model shaping 团队产品经理已用心写好的文档……

在她审阅之前先拿出一个相当不错的提案」<button class="pd-ts" data-t="05:38" data-who="Nicolina" data-en="I can of course sit down with the product manager from the model shaping team Or I can look at the documents that she's already thoughtfully composed about their entry points and how they use SDKs and how" aria-label="回原文"></button>——利用别人已经沉淀的工作，而不是让她从头陪聊。

**skills(技能)**：放与具体代码无关、团队通用的事。

比如一个「竞品新闻报告」技能，每天早上跑一分钟，汇总过去 24 小时各家模型实验室的动态，Nicolina 喝咖啡时读。还有「sprint 结束状态报告」：

过一遍所有项目，自动生成已发布、进行中、下一步的更新——以前要 10 到 30 分钟排查，现在几分钟输入提示词就行。

仓库接的模型不是锁死一家的：最初用 [[Claude Code|Claude Code]],但现在很多开源 [[harness|harness]] 都能读同一套 Markdown。

他们正转向更多用自己的[[开源模型|开源模型]]——一来模型好用，二来「Anthropic 和所有这些其他模型正开始变得相当昂贵」<button class="pd-ts" data-t="08:08" data-who="Nicolina" data-en="like many teams are learning across the globe that Anthropic and all these other models are starting to become quite pricey. This is an example of using OpenCode." aria-label="回原文"></button>。

## 谁维护？规则很简单

过期上下文是最怕的事。他们的答案：

谁的领域谁负责(沙箱、客户智能归 Nicolina);战略会议由指定的人把会议产出翻译成 Markdown;方向大转弯时 CEO 会明确写信，那是更新信号<button class="pd-ts" data-t="10:02" data-who="Nicolina" data-en="But the CEO will write letters or write documents of direction, and that's a very clean moment. You know when direction is being set, and I think that speaks a lot to how well our leadership communicates direction." aria-label="回原文"></button>。

除此之外像普通代码一样靠 PR:「如果有人主动创建一个 PR、更新 Markdown 文件，那就是那么回事」<button class="pd-ts" data-t="10:28" data-who="Nicolina" data-en="I think, quite a bit, but I think if anyone else makes a PR, it's like any other PR. It's like if somebody takes the initiative to create a PR, make the update to the markdown file, then that's that." aria-label="回原文"></button>。

技能放哪也有一套规则：**离工作最近的地方**。

引用代码的技能放在对应团队的仓库里；其余的先放个人分支试用——「我会看我是否会用上它几次。

如果你确实用了，就把它推到 main」<button class="pd-ts" data-t="11:42" data-who="Nicolina" data-en="and you say, okay, first I think this is relevant. I think this is repeatable. I'll see if I use this a few times." aria-label="回原文"></button>——超级小众的就永远留在分支里。

## PM 现场演示：从一句抱怨到生产级 PR

Pavneet(基础设施产品经理，前 Amazon)走了一遍完整流程。

他的划分是：**做决策的环节高度人工，执行环节全自动**——「定义功能、定义 API 表面积、定义抽象层，那些是非常需要[[人在回路|人在环]]的……

写代码、执行的部分才是被自动化的」<button class="pd-ts" data-t="16:57" data-who="Pavneet" data-en="Which do you feel like are more automated? Yeah. So the way we see it is the part which is where the decisions are being made, right," aria-label="回原文"></button>。

第一步，功能调研技能同时接入 Pylon(支持工单)、Linear(项目管理)、Notion(内部文档)。

他输入一个真实问题——多少客户在抱怨共享存储无法扩缩容——几十秒后报告回来：

过去六个月大量客户提过，仅过去两个月就有 19 张工单；

还发现这功能其实已被部分实现但坏了、停了，「所以现在我没有在重复、没有在复制别人的工作」<button class="pd-ts" data-t="22:21" data-who="Pavneet" data-en="So we stopped working on it. So now I'm not duplicating. I'm not like replicating work." aria-label="回原文"></button>。

手动做这些「很容易占掉我半天时间，甚至更多」<button class="pd-ts" data-t="23:09" data-who="Pavneet" data-en="What do you give this out of one out of 10? Yeah. So if I had to do this manually, this would have easily occupied half of my day, if not more." aria-label="回原文"></button>;再点进 Customer Insights 工具看客户 Moonlake 的通话记录，五分钟就摸清痛点——以前要一整天。

第二步，[[PRD|PRD]] Writer 技能：

接受调研产出、可选吃进一个 UX [[原型|原型]]，然后对 Pavneet 做**逐轮访谈**——而且被特别指示「要推动我、在我的假设和决策上挑战我」<button class="pd-ts" data-t="21:13" data-who="Pavneet" data-en="you know, to push me, to challenge me on my assumptions and basically the decisions I'm making." aria-label="回原文"></button>,还配了题库(有哪些权衡？

有没有单向门决策？)。「它不是我的替代品，但它确实做两件事：加快整个 PRD 撰写，很大程度上解决空白页问题；

还捕捉到很多我可能没想到的东西」<button class="pd-ts" data-t="31:14" data-who="Pavneet" data-en="So here's where your domain expertise, your human judgment is coming in. Yeah, like it's not a substitute for me, but it really does two things. A, it speeds up the whole PRD writing," aria-label="回原文"></button>——比如它主动提出缩容后计费要立即调整，这是 Pavneet 最初没想到的。

第三步，UX 原型技能：把一页纸 PRD 转成详细提示词，丢进 Figma Make 生成可点的东西。

因为人人能可视化方案，「很多最好的批评性反馈正是来自那里，来自工程、市场或其他任何人」<button class="pd-ts" data-t="29:54" data-who="Pavneet" data-en="visualize the solution, see how it's going to interact with the user. And that's where we find a lot of the best critical feedback comes from engineering, marketing, or anybody else." aria-label="回原文"></button>。

这背后是他们重新定义了 AI 时代的 PRD:不再是 Amazon 式的 20 页把关文档，「而是用来触发构思和解决问题的工具」，一到两页，定义客户问题、列方案选项、给一段示例用户旅程<button class="pd-ts" data-t="28:15" data-who="Pavneet" data-en="A little bit differently where it's a tool to trigger ideation and problem solving. That's it. And it's short." aria-label="回原文"></button>。

「取代我们历史上六页纸大部分内容的，其实是一个原型」<button class="pd-ts" data-t="29:16" data-who="Pavneet" data-en="So we are used to rising like 20 pager PRDs. What replaces the bulk of that is actually a prototype. So we built a separate skill." aria-label="回原文"></button>。

最后一步，PR:因为工程团队维护着一个完整的工程仓库——架构细节、runbook、历史设计文档都以技能形式开放给 Claude——「它能够在第一次尝试时就构建出高保真的 PR」<button class="pd-ts" data-t="19:08" data-who="Pavneet" data-en="design documents, which Claude has access to through our shared repo. And that's why it's able to build high fidelity PRs in like a first attempt, really. Wow." aria-label="回原文"></button>。

过程中它派生多个子智能体分别检查数据平面、控制平面和文档，中途向 PM 要 PRD 或原型。产出也不是直接可用：

最终 PRD 顶部明确标着「草稿」，用户旅程里混进了内部实现细节，仍需 PM 编辑——这正对应「探索设计阶段人在环」的流程设定。

## 负责人的「上帝视角」：Orchestrator

Charles 日常不用钻进任何单个仓库。

他用内部工具 Orchestrator:公司所有主要仓库都在一个界面里，可以自选 harness(OpenCode / Claude / Cursor)和模型(他自己偏好 GLM + OpenCode),随口问「model shaping 产品最近启用的微调模型是什么」——它后台起一个沙箱、克隆必要的仓库片段、探查代码，一分钟给出答案(最新的是 NVIDIA Nematron Super 120B)<button class="pd-ts" data-t="38:13" data-who="Charles" data-en="it looks like the answer is the last model that we enabled for supervised fine tuning is the new NVIDIA Nematron Super 120B model. So I can do this exercise essentially across any product," aria-label="回原文"></button>;发现小问题还能直接从这里生成 pull request。

关键设计是它**继承每个仓库本地的 skills 和 MCP 服务器**，「我不想为了做一个小改动，就把所有这些都构建进我本地的 open code 里」<button class="pd-ts" data-t="39:18" data-who="Charles" data-en="of those repos. So I don't want to have to build all that into my local open code just to make one small change. It's a lot simpler to just use orchestrator." aria-label="回原文"></button>。

它服务的是「休闲用户」：只是想回答一个问题、解决一个麻烦的人。这背后是他们对共享度的反思：

「我们基本搁置了存在一个巨大的、大家都泡在里面的平面上下文的构想——它更像一个上下文层级结构，有些人属于最深处，有些人只想在顶层穿行」<button class="pd-ts" data-t="41:01" data-who="Charles" data-en="And they're really not interested in the rest. So we sort of set aside the idea that there is one big, broad, flat set of context that we're all going to swim in." aria-label="回原文"></button>。

想复制？Hassan 说 Orchestrator 大概花了几周到一个月工程时间；必备件是：

接入所有仓库、继承各团队的 MCP 和技能、沙箱机制(每个调研或 PR 都在沙箱里克隆仓库片段完成)、再加一个模型网关/路由器——「每一个组件要么构建起来相对快捷，要么有开源工具，要么有商业软件」<button class="pd-ts" data-t="44:06" data-who="Charles" data-en="every one of these components I've mentioned so far, either it's relatively quick to build, There are open source tools and libraries that let you do these things." aria-label="回原文"></button>。

## 最后一环：拿智能体当测试用户

Hassan 团队的 Agent Evals 在发布后验证产品对智能体是否好用：

起一个沙箱跑 Claude Code,给它真实任务(比如「用这个数据集跑微调任务，部署成专用 endpoint,发推理请求评估，完了删掉」)，然后看它能不能做成。

一次运行发现智能体找不到「可微调模型列表」的文档页——翻完整转写记录才发现那页没被链接，于是提 PR 修文档。

这类工具已经带来了几十处文档修复。

Charles 认为这是产品验证方式的质变：

过去要等用户测试、收到一堆矛盾信号才能知道设计对不对，而且「对我们很多产品来说，智能体已经是主要用户了」<button class="pd-ts" data-t="50:38" data-who="Charles" data-en="And here essentially, at this point for a lot of our products, agents are already the majority user. And so the idea is that the nice part about that is now," aria-label="回原文"></button>。

「无论你的文档说你的产品是什么，你都可以确信它实际上就是那个样子，因为每隔几个小时我们就有智能体重新验证这一点」<button class="pd-ts" data-t="51:02" data-who="Charles" data-en="And it's really powerful to have the confidence to know that whatever your documentation says your product is, you can be sure that it actually is that" aria-label="回原文"></button>。

他说这就是他们这类产品「用户体验的新标准」。

如果产品偏图形界面，就得换用能点击、解读屏幕的视觉推理模型，但思路可平移。

## PM 和工程师的边界变了吗？

Akash 追问：产品经理到哪为止、开发者从哪开始？Charles 的答案出人意料地保守：

「每件事的本质，今天和 AI 出现之前并没有太大不同」<button class="pd-ts" data-t="54:11" data-who="Charles" data-en="the long-term architectural strength of the product. The essence of each thing I don't think is actually all that different today than it was before AI." aria-label="回原文"></button>——产品人的核心仍是带来经过充分验证的、关于市场的独特洞见；

工程师的核心仍是拿出最高效、可维护、利于长期架构的设计。

**变的是两边伸进对方领域的便捷度**:PM 能深入实现、提交 PR,工程师也能用 Customer Insights 自己做客户分析、建常驻查询。

至于生产力到底涨多少，他很克制：「我肯定可以说我们的速度提升超过了 5%。

我觉得那些说 3 倍的说法非常可疑」<button class="pd-ts" data-t="56:05" data-who="Charles" data-en="But I would definitely say that our velocity has gained more than 5%. I find claims of 3x to be very suspicious. When you get a team of," aria-label="回原文"></button>——探索、辩论、协调这些环节「并不会因为 AI 而神奇地变好」<button class="pd-ts" data-t="56:29" data-who="Charles" data-en="Coordination. And a lot of these things don't get magically better with AI. So even if you compress the research and even if you compress the coding and" aria-label="回原文"></button>,压缩研究和编码已经很值了。

  //    pathname → spaNavigated 永远置不了 true。window 上用「未设置才记」守卫,只在**第一次**记真·落地路径,
  //    重执行/换页都存活;__pdSpa 一旦置 true 就 sticky。referrer 用整 origin 比对(new URL),防
  //    「本站origin.evil.com」前缀欺骗(GLM 011[2])。
  if (window.__pdLanding == null) window.__pdLanding = location.pathname; // == null 兼捕未设置态,且不把该字面量带进页面(既有「页面无脏词」闸门)
  function pdSameOrigin(u){ try { return new URL(u).origin === location.origin; } catch (e) { return false; } }
  function direct(){
    if (location.pathname !== window.__pdLanding) window.__pdSpa = true; // 跳到别的页 = 站内导航(sticky)
    var fromSite = pdSameOrigin(document.referrer || '') || window.__pdSpa === true;
    document.body.classList.toggle('pd-direct', !fromSite);
  }

<script>
(function(){
  function fmt(s){
    if(!isFinite(s)||s<0) s=0;
    var m=Math.floor(s/60), x=Math.floor(s%60);
    return (m<10?'0':'')+m+':'+(x<10?'0':'')+x;
  }
  function wire(box){
    if(box.dataset.wired) return; box.dataset.wired='1';
    var a=box.querySelector('audio'), pb=box.querySelector('.pb'),
        bar=box.querySelector('.bar'), fill=box.querySelector('.bar > i'),
        tm=box.querySelector('.tm'), t2=box.querySelector('.t2');
    if(!a||!pb||!bar||!fill||!tm) return;
    var total=0;
    function paint(){
      var cur=a.currentTime||0;
      fill.style.width=(total?(cur/total*100):0)+'%';
      tm.textContent=fmt(cur)+(total?' / '+fmt(total):'');
    }
    a.addEventListener('loadedmetadata',function(){
      total=a.duration||0;
      if(total&&t2) t2.textContent=Math.round(total/60)+' 分钟 · AI 合成朗读';
      paint();
    });
    a.addEventListener('timeupdate',paint);
    a.addEventListener('play',function(){ pb.textContent='❚❚'; pb.setAttribute('aria-label','暂停'); });
    a.addEventListener('pause',function(){ pb.textContent='▶'; pb.setAttribute('aria-label','播放'); });
    a.addEventListener('ended',function(){ pb.textContent='▶'; });
    pb.addEventListener('click',function(){ if(a.paused) a.play(); else a.pause(); });
    function seek(ev){
      if(!total) return;
      if(ev.clientX==null) return;
      var r=bar.getBoundingClientRect();
      var x=Math.min(Math.max(ev.clientX-r.left,0),r.width);
      a.currentTime=(x/r.width)*total;
      paint();
    }
    bar.addEventListener('pointerdown',function(ev){
      seek(ev);
      function mv(e){ seek(e); }
      function up(){ document.removeEventListener('pointermove',mv); document.removeEventListener('pointerup',up); }
      document.addEventListener('pointermove',mv); document.addEventListener('pointerup',up);
    });
    a.addEventListener('error',function(){
      box.classList.add('pd-play-dead');
      box.textContent='本集中文精华音频还没生成好,稍后再来听。';
    });
  }
  function all(){ document.querySelectorAll('.pd-play').forEach(wire); }
  document.addEventListener('nav', all);
  if(document.readyState==='loading') document.addEventListener('DOMContentLoaded', all); else all();
})();
</script>

# 管理者日程突然能写代码了：CTO 的通宵智能体工作流

每周 15 个以上固定会议、7 个直属下属、家里还有个刚学步的孩子——这样的日程，过去几个月却能持续每周交付 2 到 10 个代码提交。说这话的人是 Hirsh Agarwal,[[The Browser Company|The Browser Company]](Arc 和 [[DIA|Dia]] 浏览器的开发公司)的 CTO 和联合创始人。他在一场 AI 工程大会上分享的核心主张是：随着[[编码智能体|编程智能体]]变得足够自主，Paul Graham 所说的「[[管理者日程|管理者日程]]」突然变得可以用作构建时间——**动手构建现在成了领导者工作的一部分**。

## 为什么领导者必须自己动手构建

第一层原因来自技术本身：现在产品的核心技术是每三个月就迭代一次的[[前沿模型|前沿模型]]，每个新模型的能力边界、对提示词的反应方式都在变。Twitter 上和公司内部关于「新模型什么好什么坏」的意见满天飞，而 Hirsh 的经验是：**除非你亲手投入其中、整天使用，否则根本无法判断一个新模型适合做什么**。这些直觉决定了你如何指导工程师、如何调整产品和战略、三到六个月后开源模型追上来时怎么办。

第二层是沟通效率：就算你建立了直觉，也很难传达给没把玩过模型的工程师——你说「这个东西现在可能了」，对方只会敷衍「行吧」。而拿出一个能跑的原型让他们亲手把玩，比每三个月说服一次要快得多。

而且领导者恰恰是最适合做这件事的人：你掌握着全组织最多的关于业务、战略、取舍的上下文，所以「你给模型写提示词时，领导者的引导作用按每个 token 计算比 IC 更有影响力」。委派技能也能直接迁移——设定目标、给背景、跟进检查、甚至辅导[[智能体|智能体]](「你要不要试试这个？

」)。当下的模型执行很强但判断力不行，经常回来说「这个算法想法不可行」，需要你补一句「你试过那个方法吗」，模型立刻就通了。

## 领导者该构建什么：四类 + 一条红线

Julie Zhou 一个月前调查了一批湾区技术领导者，总结出四类适合领导者的构建：①内部工具和效率改善(给代码库做园艺)；②表彰团队的小作品；③最重要的——愿景类，亲自把玩新模型家族、 visceral 地理解什么是可能的，再做成原型展示给工程师，突破产品和业务的边界。

Hirsh 补了一条红线：**不要接任何关键路径的工作**。你会被拽去救火、招人电话和会议，最不该让关键工作依赖你。

## 每天两三小时怎么安排

他的节奏是三块：**早间约一小时编码时段**，评审昨晚智能体的产出；白天在会议之间穿插几个 15-30 分钟的**引导时段**；最重要的是**下午 5 点的时段**——设置好当晚要跑的通宵任务。

通宵循环长这样：5 点收集上下文 → 设置任务、回答澄清问题 → [[Claude Code|Claude Code]](或你用的编码智能体)夜里连续干四到八小时 → 早上收到一份报告，你决定怎么处置，然后发布。

## 怎么给智能体足够的上下文

对他帮助最大的思维转变：不再想「我如何拆分这个功能、教它做各个小任务」，而是想「**这个前沿模型需要什么样的全部上下文，才能像我一样做决策**」——因为夜里干六八小时时你不在场。

一个实用技巧：下午三四点，对着连接了 Slack、Jira、Notion 和代码仓库的协作智能体(他推荐自家的 Dia,还自嘲「完全没有偏向」)说一句「我真的很想构建这个，花 20 分钟翻遍 Slack 和 Notion,给我生成一个可以粘贴进 Claude Code 的提示词」——30 秒语音输入，换回一个包含全部权衡、历史尝试、业务背景的巨型提示词，直接粘进编码智能体。

然后是验证设计：**先写测试**(事后写的测试会有点马虎)；让它用 [[计算机使用|computer use]](让模型自己操作屏幕点击验证)测试端到端流程是否真的解决业务问题；要求拆成对审查者友好的 PR、管好 CI 并保持绿色。还要让它在一个干净的子智能体里跑一遍 AI 代码审查 skill,修掉问题;盯着 PR,自主解决每条机器评论和 CI 检查，「不要问我问题」。他还会加一句鼓励：「你会做得很棒的，我相信你」——不知道有没有用，但他习惯这么做。

他的结论：「新模型能在一次过夜运行中处理过去需要几周的工作量，早上你会得到一份准备好的漂亮礼物」。

## 三个实例：功能、评估爬坡、训练模型

**实例一：构建功能**，就是上面的流程。

**实例二：优化 AI 功能。** 原型上加个反馈按钮和小文本框，白天抽空收集反馈，让它把每次运行的 system prompt、输入和你的反馈存成 JSON 转储——哪怕只收集 4、5、10 份都行，拉上同事能到 20、30 份。

然后 5 点下指令：把这些变成[[评估|评估]]集(本地 SQLite 或 Markdown 就行)，交互式地对齐评分设计，再构建一个 harness 反复[[爬坡|爬坡]](hill climbing,即自动迭代提示词直到评分上涨)直到分数上升。数据这么少肯定担心过拟合——「但你只要告诉它不要过拟合，它实际上做得相当不错」。

再让它把这个流程存成可复用的 skill。他们内部的代码审查器就是这样靠隔夜运行把质量爬上去的，推到员工试用和生产环境后确实提升了质量。

**实例三：隔夜训练自定义 ML 模型。** 他们要做一个 PII(个人身份信息)分类器，试了 Opus 和 Haiku,成本高、延迟差、精确率召回率上不去。

于是某个晚上，Hirsh 给出一堆业务背景和训练数据，让 Claude 清洗数据、用合成数据补充、给一堆密钥用多模型组合推质量；因为「我完全不知道什么 ML 模型合适，所以你来决定」——而且「别只训练一个，训练两个」。关键安全设置：只给 AWS 的预置[[沙箱|沙箱]]权限，「不要给生产环境权限，那样你会把生产环境搞挂的」；挑 GPU、开 EC2 集群、训练、对照评估样例测试、销毁资源，甚至连模型就绪后如何接入代码库做推理都一并写好。早上醒来：两个训练好的模型、一份完整报告，其中不少已经推到生产环境。

## 最大的收获与前提条件

做这些事最大的收获是**突破任务范围的边界**：他引用 Notion 创始人 Simon Last 的推文——「这些现代模型能做的事情远远超出我们的想象」。领导者的职责就是理解模型能力的轮廓，不断尝试给智能体更大的范围，看看几周、几个月的工作能不能隔夜完成。

但要泼一盆冷水：这一切能行，很大程度上靠**已有的组织脚手架**——AI 代码审查器、干净的 Claude.md 和 agents.md、可信任的 CI、精细的功能开关，以及一个推给员工但不进生产的原型分支，层层隔离保证你做原型时不会搞挂生产环境。

代码卫生也真的重要，他坦承自己「已经被打脸很多次」，代码惹恼过工程师、造成过线上事故。几条实战建议：PR 提交前自己测试一切(computer use 再好也替代不了你自己点一遍)；提交小而可读的 PR——因为你在向团队示范什么是好的标准，你挂三个 5000 行的 PR,别人也会开始这么干；最后，**别把还没读过的代码交给其他审查者**——代码里一定有某个明显糟糕的东西，某个资深工程师会打电话问你「你为什么不读一下？」他强调这是亲身经历。

## 本集带走

- **管理者日程可以当构建时间用**：每天早间 1 小时评审 + 白天零星引导 + 下午 5 点设置通宵任务，2-3 小时就能持续交付。
- **给上下文，不是给任务拆解**：核心问题是「模型需要什么上下文才能像我一样决策」；用协作智能体花 20 分钟翻 Slack/Notion 自动生成巨型提示词，30 秒语音就能触发。
- **验证前置**：先写测试、用 computer use 跑端到端流程、要求拆成小 PR 并保持 CI 绿色、让干净的子智能体跑 AI 代码审查。
- **三个可复制的通宵任务**：构建整功能；收集十几份反馈 JSON 让它自建评估集并爬坡优化提示词；给沙箱权限让它隔夜清洗数据、选型并训练自定义 ML 模型——记得「训练两个」。
- **绝不接关键路径的工作**；构建目标是内部工具和愿景原型，原型分支只到员工端不进生产。
- **卫生就是领导力**：小 PR、亲测每一行、审完再拉人——你在示范整个团队的「什么算好」。

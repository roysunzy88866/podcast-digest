===标题===
用 Cursor 重构遗留代码库：一次 PHP 迁移 React 的完整实操
===导语===
Cursor 现场工程师 Amrita 演示重构遗留代码库的四步法：审计规划、拆工单、云端智能体执行、自动化守护。
===正文===
这是一场 Cursor 官方研讨会，主题是怎么用 AI 重构那些没人敢碰的遗留代码库。主讲人 Amrita 是 Cursor 的现场工程师（来 Cursor 之前她是软件工程师），她当场把一个 WordPress 开源仓库里的 PHP 遗留组件往 React 迁移，完整走了一遍全流程。她开场就点明 Cursor 最大的差异点之一：云端智能体（Cloud Agents）——你启动一个智能体后可以合上笔记本去散步，它在远程机器上继续跑，做完还会用视频、截图和测试来证明自己真的做对了 [06:06 Amrita]。

**Cursor 不只是模型，还有中间那层 harness**

为什么非要用 Cursor 做大型迁移？Amrita 的回答分三层。第一层是平台：除了 VS Code 的 fork IDE，还有智能体窗口、CLI、云端智能体和 iOS 移动应用（Android 即将推出），甚至可以接进 Slack——Cursor 内部就有一个 Slack 里的智能体，专门检查在线文档和实现是否脱节，发现不同步就自动开 PR [06:40 Amrita]。第二层是模型灵活性：所有前沿实验室的模型加开源模型（Kimi、GLM）都有，还有自家模型 Composer。她特别推荐刚发布的 Grok 4.6——它的强大程度对得起价格，而且比起其他前沿模型，执行长任务时非常便宜 [08:10 Amrita]。第三层最容易被忽略：Cursor 的 harness（工具执行、缓存管理、动态上下文管理等一整套中间层），这才是让模型在重构大代码库时真正好用的原因，「远不止模型和平台」[10:39 Amrita]。

模型灵活的实际用法是**混搭省钱**：她举了 Cursor 内部的案例研究——用智能体集群从零重建 SQLite，组合「重型模型做规划 + 执行导向模型写代码」，比单独用任何一个贵模型都便宜得多。她的具体偏好：写规划文档用 GPT-5.6 Sol（写作更好），云端跑迁移用 Grok 4.6 或 Composer，Anthropic 的模型「往往比较贵」就避开 [33:32 Amrita]。

**四步法：审计 → 规划 → 拆工单 → 云端执行 + 自动化收尾**

**第一步，用 Canvas 审计代码库。** 输入斜杠命令 `/canvas`，它会分析整个代码库的测试覆盖率，标出缺口，并生成交互式可视化——哪些管理页面该先迁移、哪些 client.js 没有单元测试、新测试该怎么组织，全部分类列好。Canvas 可以随时改（「把它变成柱状图」一句话就行），可以发布链接分享给同团队的人，还能下载成 PDF。她喜欢在动手迁移之前先跑一遍这个，因为它能「非常快速简便地把代码库可视化」[19:15 Amrita]。

**第二步，用 plan 模式做迁移策略。** 关键是让模型换到写作好的模型，然后明确提出要求：迁移哪些组件、要加测试防回归，还要它画出「当前现状架构图 + 迁移后目标架构图」（默认用 mermaid 图，也可以接 Lucidchart、FigJam 输出）。plan 模式的铁律是：**它永远不写代码，只产出一份 markdown 策略文档** [17:52 Amrita]。它会用 Ask Question 工具尽早向你要方向——比如「遗留组件太模糊，范围是什么？」；你可以把它设置成动手前至少问你五个问题。

**第三步，用插件把计划拆成 JIRA 工单。** 通过 Atlassian MCP（MCP 即把外部工具接进智能体的连接器），一句话就能把计划拆成一整套带目标、范围、验收标准、依赖关系的 JIRA epic。Cursor 里现在还有 Datadog、Figma、Google Drive/Calendar/Gmail 等插件，装插件还会自动附赠官方 skills（预置的工作技能）。

**第四步，交给云端智能体执行。** 在 cursor.com/agents 里选中仓库，一句话：「找到看板上指派给我的所有 JIRA 工单，全部处理，每个工单单独开一个 PR，用截图或视频验证你的更改」[33:00 Amrita]。几个关键细节：

- **多仓库是巨大差异点**：一个云端智能体可以跨多个仓库工作，适合微服务架构或「改一个内部 SDK、所有客户端服务都要跟着更新」的场景 [30:16 Amrita]。
- **环境搭一次就缓存**：首次搭建远程环境要 10 到 20 分钟，之后通过 build 保存快照，后续秒启动。
- **它有自己的电脑和鼠标**：云端智能体跑在 Linux VM 上，能自己操作浏览器做端到端测试，还会给验证视频分段标注（「这是登录部分」「这是查看评论」）——这就是它自证「没引入回归」的方式。
- **成本惊人地低**：因为云端任务耗 token 多，配便宜快的模型，一整个迁移可能只花三四美元 [31:00 Amrita]。
- **千万别要一个巨型 PR**：把所有改动塞进一个几千行的 PR 根本没法 review，要的是多个 PR 各管一个组件或服务 [35:01 Amrita]。

她在 Cursor 内部的实际用法：周五把积压工单扔给智能体，周一回来 review PR；分布式团队（欧洲一队、亚洲一队）甚至可以通过云端智能体异步接力——一队睡了另一队接上 [35:34 Amrita]。

**收尾用自动化（Automations）防止代码库再烂回去**。自动化就是「被调度或被触发的云端智能体」，可按时间、事件（PR 打开、标签变更）、Slack/Teams 消息或自定义 webhook 触发。她现场演示了自己当工程师时就想要的「feature flag 清理器」：每周扫一遍仓库，找出 30 天没用的陈旧 feature flag，和 Datadog、Sentry 交叉核对确认没问题，然后开 PR 删除并附上无回归的测试，完事发 Slack 通知 [42:23 Amrita]。还有现成模板：事件调查自动化可以代替凌晨三点叫醒 on-call——它先做初步调查，再把摘要发给值班的人 [44:35 Amrita]。她的工程哲学是：代码库烂掉往往就是因为不够主动、依赖没人更新，自动化让智能体提前把事做掉，防患于未然 [43:45 Amrita]。

**问答里的几个实用点**：环境变量、API 密钥、IP 白名单都配在云环境设置里；内网服务可通过 AWS PrivateLink、Cloudflare Tunnel、Tailscale 等私有连接方案接入（文档里叫 private connectivity），也支持自托管但官方不作为首选推荐；想让 Cursor 记住团队的编码风格，装 Continual Learning 插件，它会往 agents.md 里持续积累；每个自动化还有自己的 memories.md 文件，会从你每次的反馈里学习，越跑越准 [55:10 Amrita]。她最后给的建议很直接：如果还没用过云端智能体，去 cursor.com/onboard 花几分钟连上 GitHub 试试——「这可能是很长一段时间以来我在任何 AI 产品里见过的最好的功能之一」[47:54 Amrita]。

## 本集带走

- **四步流程照抄**：`/canvas` 审计测试覆盖 → plan 模式出策略（含现状与目标架构图，且它不写代码）→ Atlassian 插件拆成带验收标准的 JIRA 工单 → 云端智能体按工单逐个执行、一工单一 PR。
- **模型按角色混搭省钱**：规划用写作好的模型，云端执行用便宜快的（Grok 4.6、Composer），避开贵的；整个迁移可能只要三四美元。
- **一句话派活的关键措辞**：「找到指派给我的所有工单，全部处理，每单一个 PR，用截图/视频验证无回归」——要求它自证，并强制多个小 PR。
- **用自动化防复发**：定时扫陈旧 feature flag、依赖更新、漏洞扫描、事件初步调查，都有现成模板，让智能体提前做事而不是事后重构。
- **内网也能用**：私有连接走 AWS PrivateLink / Cloudflare Tunnel / Tailscale；密钥和 IP 白名单配在云环境设置里。

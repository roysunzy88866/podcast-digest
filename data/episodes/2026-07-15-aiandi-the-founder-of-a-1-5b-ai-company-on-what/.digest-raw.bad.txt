===标题===
Granola CEO Chris:会议笔记只是诱饵,我们赌的是一场计算革命
===导语===
Granola 联合创始人兼 CEO Chris Pedregal 与 Every 的 Dan Shipper 对谈:为什么被巨头抄袭不慌、他怎么用海盗与建筑师组织团队,以及 Dan 现在把全部工作搬进 Codex 的方式。
===正文##
这一集聊的是两家 AI 公司当家人的一次坦率交底。Chris 是 Granola 的联合创始人兼 CEO——就是那个最早让用户惊呼「这居然真的能用」的 AI 会议笔记应用,团队已到 60-70 人、以约 15 亿美元估值融资。对面的 Dan Shipper 是 Every 的 CEO,一个把全部工作都搬进 Codex 的重度实验者。Chris 开场就先泼冷水:创业就像持刀搏斗,而他以前以为创业只有做不成的时候才难——结果发现,做得好的时候也同样难 [02:30]。

## 被抄袭不可怕,因为大家抢的东西不重要
Notion、OpenAI、Zoom 都陆续上线了深受 Granola 启发的会议笔记功能,但 Chris 说这些对他的增长曲线几乎没有影响。他的视角拉得很远:我们正处于一场计算革命非常非常早期的阶段,迄今为止出现的一切,与即将到来的一切相比都会黯然失色 [06:10]。会议笔记并不是所有人都在追逐的那种终极价值,有比这大得多的东西——我们用什么界面来工作、在 AI 原生的世界里工作会是什么样 [06:23]。今天人们争夺的东西并不重要;他也承认 Granola 本来就不是第一个做会议笔记的,「你们怎么敢被我启发」这种话他说不出口,这就是生态系统 [07:21]。

## 组织 70 人:海盗与建筑师,以及砍不掉的头衔
Chris 上一家公司 Socratic 只有 12 个人,现在团队翻了几倍,他说最大的挑战就是「组织人」这种从没做过的事。其中最难的一个问题:当你谈论产品要有灵魂、要有一致性和品味时,人多了怎么规模化这种东西?他反复琢磨 PM、设计、工程这些传统角色是否还该一一对应地存在。

Dan 提供了一个他认为对早期产品很有效的心智模型:**海盗与建筑师**。海盗的职责是尽可能快地构建、去发现有价值的东西——可以用 vibe coding(用自然语言让 AI 生成代码)写出来,不用管架构;建筑师与海盗配对,当海盗发现有价值的东西后,把它变成可持续、可理解、可规模化的系统。有趣之处在于:每个产品需要一个海盗,但一个建筑师可以同时管多个产品——现在的工具太好,好的架构师一小时就能用 Claude 摸清一个陌生代码库,然后派 Codex 去做 24 小时的重写,自己去做别的 [11:36]。海盗是技术、产品设计等的混合体,建筑师主要专注技术侧;真正的产品则由一个设计团队空降进去帮忙打磨 [12:31]。

Granola 自己的做法是功能分阶段:先「塑形」——从待完成的任务出发,尽快探索尽可能多的解决方案形态,然后诚实地自问「人们真的会雇用我们做这个吗」;再「验证」——对少数人证明你确实有用、他们愿意选你;通过了才投入把它做好、做可靠、做可扩展。这松散地受了 Basecamp 的 Shape Up 方法启发,但 Chris 回读时觉得那些例子已经很过时——不过核心想法仍然可靠 [13:43]。至于头衔,他们仍有设计师、PM、工程师之分(全公司约 3 个 PM),Chris 一直在琢磨砍掉它们,因为项目上真正需要的是「有人负责审美、有人负责构建、有人负责策略」,可以是同一个人也可以不是——但没有角色又会有大量沟通开销。没有答案,继续实验 [16:11]。

## Dan 的工作方式:两个界面,Codex 是承重墙
Dan 的工具栈极简:几乎所有时间都在 Codex 里,大约两三个月前开始的;Claude 桌面应用偶尔用。他的总体判断是**工作正在分化成两个界面**:一个是异步委派型工作——发生在 Slack 里,协作的、多人的、有时是主动的,通过机器人完成,比如每天早上发帖汇报解决和上报的 bug、推送的 PR,你可以像对待同事一样当场派活,而且关键是可以在公开频道里做——大多数 AI 现在都是单人使用的,公开协同时一件很有意思的事 [20:04];另一个是严肃工作的界面——你和智能体坐在同一个应用里,比如 Codex 或 Claude 桌面应用。

Dan 几乎所有软件都在 Codex 的应用内浏览器里使用。他给了一个心智模型:所有始于开发者的模式,最终都会进入所有知识工作——因为构建一个足够好的智能体来构建软件,一旦能做到,它就同样适合任何知识工作,这正是 Claude Code 变成 Claude Cowork 的原因 [21:44]。最生动的例子:他最近搬家换网络,直接让 Codex 去办——Codex 在内置浏览器打开 Verizon 网站、拿着密码登录、和对方(八成也是 AI)的客服聊天,处理各种追问,知道他不要任何隐藏费用、会算账、会推动对方给出该给的方案,全程他只是坐在那儿 [23:02]。邮件也一样:邮件变成一张张卡片,每张写着「这是邮件内容、我认为回复该这么写、要发吗」,他直接对着卡片说话——这是他用 vibe coding 搭的开源实验品 Tend,之后会在他们的邮件客户端 Quora 里做成开箱即用的功能。

他把这类应用叫 **codex 原生应用**:应用只负责保存状态和渲染 UI,你把自己的智能体带到它上面。这个范式和 MCP(让智能体调用外部工具的协议)的区别在于:MCP 历史上是「智能体去和这个应用交互,而我不去」;这个范式要的是**智能体和用户同时与这个应用交互、能互相交替**——给智能体一个 MCP 或 CLI,给用户一个网页界面,关键难点是 CLI 的操作必须实时反映到用户看到的 UI 上 [28:04]。在场感也很真实:他们的 Markdown 编辑器 Proof 里,你能看到 Codex「进入」了文档、看到它在哪儿——实现就是一条「设置在场状态、设置位置」的命令,智能体非常擅长用 [29:52]。

## Granola 的应对:做最好的上下文捕获者,而不是所有智能体
Chris 的策略很明确:计算的新时代里,计算机第一次能理解我们的上下文,而正确的上下文决定了你能从 AI 里获得多少价值。所以 Granola 的上下文应该尽可能开放——你想在 Codex 里用、在个人智能体里用都行,他们的 API 和 MCP 接下来几个月会大幅变好,这是一等目标 [39:01]。同时,在少数与会议相关的事情上要比世界上任何人都好 5 倍,把该现场使用的 UI 场景做透。他举了个用户例子:一位做销售的用户,用 Claude 在见客户前生成一个样式模仿客户网站的微型网站,再通过 Granola 的 MCP 拉取全部会议上下文填进去——这种事 Granola 永远不该追求做到世界最好,但用户照样在 Granola 里写会后跟进邮件,两类都可以成立,不是二选一 [40:53]。

「扶手」是 Granola 内部关于产品感觉的核心隐喻:楼梯的扶手平时隐形、你从不注意它,但绊倒那一刻你的手会本能伸出去,它必须正好在那儿、必须能承重 [36:39]。所以他们会预先以「夸张到离谱」的量生成会前简报(这个人是谁、上次聊了什么),实际被打开的只占很小比例——但价值场景是你开会迟到两分钟时那 15 秒的窗口,它必须在,否则就没用了。Chris 坦承不知道怎么衡量这种「平时不用、用时承重」的功能价值,连「把功能撤掉看用户喊不喊」都不是好办法。代价观上他们现阶段对 token 花费很不在意:成本会随时间下降,等知道了最佳体验再去优化;真正的智能体功能非常贵,迟早会打破成本账,但现在优先级是找到杀手级 AI 原生体验 [56:34]。

一个根本性的设计挑战是「时间旅行问题」:智能体做事需要时间,你启动任务的时刻和审查任务的时刻是分离的,你得把全部上下文重新装回脑子。Chris 认为未来会出现高度为这个问题优化的界面,但他还没见过做得好的 [33:16]。他也认为还有一或多个**尚未被发明的规范 UI**存在:当你面对的是「今天所有会议」这个量级的上下文,而不是单次会议,正确的 UI 和交互设计是什么?没人搞清楚。聊天线程做一件事时出奇地强大,但跨不同上下文做多件事时,我们还没有正确的隐喻 [53:40]。而且新 UI 范式与其说是发明的,不如说是被发现的。

Dan 补充了他对 Granola 的期待:转写稿经常是错的、且完全捕捉不到「XYZ 说了这句话之后有一段长长的停顿」这类细微之处;如果用人体作类比,AI 是韧带和肌肉,软件必须是骨骼——骨骼给它形状和结构,AI 围绕这个做任何事 [45:29]。如果 Granola 能把「我没参加的所有 Slack 和会议」变成高保真的解读卡片,那将是世界上最有价值的东西,他甚至不需要打开这个产品。Chris 回应了一个真实的两难:Granola 已经能给每个用户生成两页的「今日状态」画像并让笔记质量大增,但那样笔记里会混入非本会议的信息——比如「他嘴上说喜欢,但我们知道他讨厌这类想法,另外五次会议说过五次」——于是「受众是谁」成了微妙问题:你自己的完美笔记,未必适合分享给别人 [48:52]。

## token 花费与用户真相
团队内部,Granola 直到 Fable 发布才第一次追踪 token 开销——因为有人发现自己一天花了几千美元;Every 那边更夸张,运营 Quora 的 Kieran 按趋势一年要花掉约一百万美元额度 [55:34]。Chris 不给团队设 token 指标,只要求把握目标精神:尽可能高产、用得深思熟虑。产品侧有个反直觉数据:**每个星期,大约一半的 Granola 用户在以智能体的方式使用产品**——比如围绕一段时间的会议做多步骤的教练式分析——只是他们自己绝不会用「智能体」这个词来描述 [57:42]。

## 本集带走
- **海盗 + 建筑师**:探索期每产品配一个「海盗」快速试错;一个建筑师可同时服务多个产品——好工具让架构师一小时摸清陌生代码库,然后丢给 Codex 跑 24 小时重写。
- **功能三阶段**:塑形(探索尽可能多的方案形态)→ 验证(对少数人证明有人愿意用)→ 才投入做可靠、可扩展。投资前诚实自问「人们真的会雇用我们做这个吗」。
- **「扶手」产品哲学**:好功能平时隐形,但用户绊倒的那一刻必须正好在那儿、能承重——代价是接受极低的打开率,并为「用时承重」型价值寻找新的衡量指标。
- **预先生成是对抗「智能体要等」的招**:用户在连轴转的工作日里不会等 20 秒,但「已经帮你生成好了、点一下就行」感受完全不同。
- **codex 原生应用范式**:应用只管存状态和渲染 UI,智能体经 MCP/CLI 进来、和用户同时操作、实时互相可见——关键约束是 CLI 的每次操作都要反映到用户屏幕上。
- **战略分工**:在少数与会议强相关的事上做到世界最好 5 倍,其余一律开放上下文给外部智能体——别人搭的工作流更好用,正是你该产品化的信号(Hugging Face 创始人关掉自己搭了几个月的会前简报工作流,就是验证)。

===标题===
浏览器自动化背后的标准之争与 AI 时代的测试危机
===导语===
Selenium/WebDriver 老兵、BrowserStack 开发者布道负责人 David Burns 讲透浏览器测试标准如何诞生，以及为什么 vibe coding 正在让生产数据库被删掉。
===正文===
让一段测试代码用同样的方式驱动 Chrome、Firefox 和 Safari,这件事背后是十几年标准化工作的博弈。这一集聊的就是自动化浏览器测试是怎么走到今天的——主角 David Burns,是 Selenium 和 WebDriver 的长期贡献者，在 Mozilla 待了十年，现在负责 BrowserStack 的开发者布道与开源。

## 从南非到 Selenium:一个 QA 的起点

David 出生在南非，大学学的是计算机科学加工业心理学的奇怪组合——他当时下不了决心当工程师还是心理学家。搬到英国后他在一家银行做流程再造，后来成了南安普敦一家初创公司的第一个 QA,那是 2006 年左右、CI 刚兴起的年代。公司给他的态度是「去帮我们把它搞明白吧，我们没时间」，于是他只好在 QA 环境里当自己的 SRE,顺便引入了当时通过极限编程兴起的 TDD(测试驱动开发，先写测试再写代码)。

他最大的悔恨是一个技术选型：当年 DSL(领域特定语言)是时尚，他给公司造了一个流式 API 风格的 DSL——就是永远「做这个点、做那个点」连起来的那种。造完一调试才发现「流式 API 简直是最糟糕的：到处都是点，打开调试器得穿那么多层才能找到真正的问题」。他的结论：别那么做，看着漂亮，但很难用。

## 把 Selenium 塞进标准：WebDriver 的诞生

David 在晚上为 Selenium 做开源(妻子是音乐家，晚上不在家)，做了大约四年后，在瑞士的 Google 测试自动化大会上遇到 Opera 的一个人，那人把 Selenium 移植进了 Opera 浏览器。全场都觉得每个有浏览器的公司都该这么干，而那人指了条路：想做到，就进标准。于是 David 和 WebDriver 的创造者 Simon Stewart 密切合作，加上 18 个月后加入他团队的 Andreas Tolfsen,开始起草规范。

难的不是「点击、输入、拖拽」这些简单指令，而是那些听起来无害的问题：你怎么知道一个元素真的在页面上？要等多久？「可见」到底是什么意思？David 说，等待问题的本质是在「标准化一个有意义的等待」和「不试图解决停机问题」(图灵那个著名的不可能问题)之间找平衡；而「可见」没法靠逐像素检查，因为 CSS 的 Z-index 并不是真正的层级，仅凭 DOM 和 CSS 的布局方式，其他东西就能覆盖上去。大量精力就花在这些「用户不必自己解决」的难题上，再留出扩展口子——比如浏览器权限弹窗(「是否允许访问摄像头和麦克风」)的测试，就是靠规范里的 WebDriver API 扩展出去做的。今天的重点则是 WebDriver BiDi(BiDi 即双向)，让自动化工具和浏览器之间能双向通信。

标准化的慢反而换来正确。他举例：有个浏览器间通信的规范已经到第三个迭代，前两版快但坑多——Firefox 打不到 Chrome——第三版慢了很多但更正确。

## 高管为什么该资助对手也在用的开源

现在很多工具——Selenium、WebDriver.io、Playwright——都建在 WebDriver 标准上，唯一原因是它们不用再操心「怎么跟浏览器对话」(当年跟 Internet Explorer 对话要做大量 COM interop,Java、Python、Ruby 下都很惨)。David 说他继续维护标准「当然让我们的竞争对手也受益，但所有人都受益，希望水涨船高」。

主持人问：怎么说服高管雇人回馈开源、连竞争对手一起抬？David 的答案是用风险说话：「所有人都停止为那些项目做贡献的风险，是最大的风险。」他提到疫情期间一个 node 包的维护者失业了、请求资助没人给，最后给包下毒并删光代码——一个项目被下毒，毒害的是整个生态。他真正的理由是企业责任：照看好让你赚钱的东西，尤其 AI 时代供应链攻击会更多；参与进去帮着保障安全，等于在给自家业务排险。另一重实际价值是人脉:BrowserStack 的产品在 Chrome 上出 bug,他能直接找到 Chrome 的人并附上复现，请对方优先处理。

## 测试哲学：每条关键路径一个扎实测试

如果你的网站只是个营销首页，谁在乎；但如果你做 SaaS(软件即服务)，David 的核心建议是：**每条关键路径只写一个测试，然后从那里扩展**。「我能登录并完成 X」这样一条测试，配上可观测性、遥测、日志这些层面的保护，远胜过 15 个大致做同样事情的测试——每个一分钟，你就白等 15 分钟。他见过太多人把测试金字塔搞成圣诞树或沙漏形状，他的解法就是这条：一个测试管关键路径、一个管无障碍、一个管视觉回归，最后可能有一百个，但每一个都是最需要的——因为启动浏览器在计算时间上极其昂贵，如今的浏览器本质上就是操作系统，「你每次启动它，都相当于在一台电脑里再启动一台电脑」。

无障碍(accessibility)是他认为被普遍低估的一块。他的论证不是法律大棒，而是生产力胡萝卜：IDE 里「不碰鼠标完成所有操作」的功力，本质上就是无障碍能力；开车时手机读短信让你语音回复，也来自无障碍工具。提升了这些体验，你就在同时解决无障碍。他还在推动一个叫 Accessibility Test Driver 的新规范——不读 DOM 推断问题(那是 AxeCore 的做法)，而是驱动真正的屏幕阅读器去操作浏览器，解决各操作系统屏幕阅读器互不兼容的老问题。

## AI 与 vibe coding:没有护栏就删你的库

David 认为 AI 时代测试会远比现在重要。他今年早些时候做过一个 vibe coding 和 vibe testing 的演讲——vibe coding 就是你写个提示词、凭感觉指望得到对的东西。问题在于：「人们会凭感觉把他们的生产数据库搞垮。」Replit 加了防护之后，人们转头用 Claude,又有人不加护栏，然后「我的生产数据库被删了」。

他的判断相当冷：「我们越把它普及化，糟糕的情况就会越严重。」原因是安全意识是被反复灌输出来的经验——C/C++ 里别访问已交给垃圾回收的变量、是否真的校验了身份验证、API 密钥有没有泄漏——从没写过软件的人没有这层肌肉记忆。所以他的立场是：**初级工程师应该少用 AI**,把它当审查用的备份，问一句「你考虑过这个问题吗」；原型谁都可以用 AI 快速搭，但进生产前必须重写或过安全检查。至于幻觉，他的话很绝对：「AI 会产生幻觉，不是可能会，是一定会。有意思的是频率，但除非你回头审查，你永远分辨不出来。」

他手头还推着两件事：把可观测性(让一次请求在应用里留下完整追踪链路的技术，如 OpenTelemetry)接进测试——看到一个失败，能顺着追踪键从「访问网站」一路复现到出问题的那一层，而不是对着日志发呆；以及还在早期阶段的 CD 事件(持续部署/交付事件)，让 CI 流水线变成事件驱动、随时可追踪。

收尾的历史趣闻：祖鲁国王沙卡训练士兵赤脚在荆棘上奔跑，目的是把脚底磨硬、让他们在真正的战场上忘记疼痛。David 的类比是：先尝试新东西，然后努力加固它——并且像在安全环境里练兵那样，在安全的环境里犯该犯的错。

## 本集带走

- **每条关键路径只写一个测试，从那里扩展**：别写 15 个互相重复的测试白等 15 分钟；关键路径、无障碍、视觉回归各一条扎实的，配可观测性和日志兜底。
- **别造流式 DSL**:链式 API 调试时每层都是一个点号，穿层才能找到真正的问题——看着漂亮，用起来痛苦。
- **向高管推开源用风险叙事**：所有人都停止贡献是最大风险，维护者下毒删库的先例真实存在；参与上游也是在给自家供应链排险。
- **AI 原型必须过安全检查才能进生产**：vibe coding 删生产数据库的故事在重复上演；初级工程师更要少依赖 AI,先让安全意识长在自己身上。
- **AI 会幻觉是确定的，区别只在频率**：不回头审查就永远分辨不出来。
- **把追踪键从测试一路带进应用**：测试失败时能复现请求全程，而不是对着日志猜怎么开始排查。

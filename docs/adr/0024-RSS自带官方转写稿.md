# ADR 0024 · 用 RSS 自带的官方转写稿取源(把 3 小时/集 变成几秒)

- 日期:2026-08-17
- 状态:已定(用户 AskUserQuestion 拍板)
- 关联:C28(user-stories)、drift #66、ADR 0014(为何不用全局配音 skill,同类「自持 vs 复用」判断)

## 背景:产量卡在 2–4 集/天,而且不是内容不够

用户问「我怎么样把内容做多?你总是一天一集」。查明真因不是没内容可抓,而是**架构物理上限**:

- 22 个源里 **19 个走 whisperX 语音转写**,项目自测 0.59x 实时 → 一集 100 分钟烧 **2.8h CPU**
- GitHub Actions **同时只允许一个跑批**(`concurrency: c7b-pipeline`)+ **单批 6h 上限**
- → 绝对上限约 8 集/天,实际 2–4 集(还要分时间做翻译、浓缩、建站)

而扫全部 feed 的 `<podcast:transcript>` 标签发现:**三个已配源本来就把官方稿挂在 RSS 里**
—— 我们在给自带稿子的播客重新听一遍。

| 源 | 带稿集数 | 格式 | 处置 |
|---|---|---|---|
| Beyond Coding | 206 / 263 | SRT(段级时间轴) | ✅ 开 |
| The Diary of a CEO | 139 / 871 | Whisper 格式 JSON(带逐词时间戳) | ✅ 开 + 题材筛选 |
| WorkOS | 28 / 31 | 纯文本(**无时间戳**) | ❌ 不用(D8 时间戳闸门无从判定) |

## 决策

1. **新增便宜通道**:取源时若该集 feed 里有带时间轴的官方稿 → 下载并转成本项目稿格式,跳过 ASR。
   失败(下载不到 / 解析不出 / 60s 超时)**一律回落 whisperX**,不抛 —— 加速通道绝不能变成新的单点故障。
2. **稿格式与 whisperX 输出同构**(扁平数组 `{start,end,speaker,text}`)→ 下游浓缩、归属闸门、
   事实层闸门**一行都不改**。`speaker` 留空(feed 稿基本不带说话人,而说话人匹配早已是软提醒,ADR 0013)。
3. **归属闸门照旧跑**(drift #60 的时长比对不依赖取稿方式)→ 换了取稿路径也不会拿错集的稿。
4. **DOAC 只收商业/科技题材**(用户拍板):源上标 `topicFilter`,标题命中词表才进库;
   判不准就跳过(少发 ≪ 发离题),漏放的人工事后可点名补(同 ADR 0021 口径)。

## 为什么这是「把内容做多」的正解

一次写好之后不止救这两个源:**以后任何在 RSS 里挂转写稿的播客都是白捡** —— 加源不必再评估
「值不值得为它烧 2.8h」。瓶颈从「CPU 小时数」变成「翻译费 + 口味筛选」,是完全不同量级的天花板。
现成存货:两源合计约 345 集带稿集可慢慢补。

## 已知取舍

- 纯文本稿(WorkOS)不用:没时间戳 → 正文出处标注与 D8 闸门失去依据。宁可继续 ASR。
- feed 稿多为节目方自动转写,准确度未必高于我们自己的 whisperX;但**引语逐字命中转写稿**这条硬闸
  仍在,稿子差只会导致金句拦下重写,不会放行失真内容。
- 题材词表是纯关键词,判不了全部情况(登记不静默)。
- 真实数据验证(本机一次性实跑,未把第三方稿内容 check 进仓库):Beyond Coding SRT 出 **351 段**
  (末段 1075s)、DOAC JSON 出 **1765 段**(末段 7848s);仓库内 fixture 结构照真实样本、文字自撰,
  刻意造出真实数据里碰不到的边角(无时间行的坏块、VTT 的 NOTE 块、内联标签)。

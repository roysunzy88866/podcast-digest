# ADR 0023 · 访问计数:自建 CF Worker + Durable Object,真实数不加工

- 日期:2026-08-16
- 状态:已定(用户 AskUserQuestion 拍板)
- 关联:C27(user-stories)、story-map C27

## 背景

用户要在首页「关于本站」下展示每日进站量(PV 口径),并问「数据量太小没面子,要不要乘以 10」。

## 决策

1. **自建免费计数器**(用户三选一拍板):独立 CF Worker `pd-pv` + Durable Object(SQLite,免费档),
   不用 CF Web Analytics(数字拉不到页面上)、不用第三方(数据在别人家)。
2. **展示「累计 + 今日」两个真实数字**(用户拍板):北京时间切日。
3. **拒绝乘以 10**:公开展示的数字造假,被对比出来(CF 后台/请求量)反而更丢面子;
   「面子」由「累计总量」这个只涨不跌的口径诚实解决。我方明确拒绝加工,用户接受。

## 为什么独立 Worker 而不进 Pages

- 计数挂了站点零影响(fail-silent:.pd-pv 保持 hidden);Pages 路由一行不动。
- ADR 0012「内容流水线不上 Workers」针对的是 cron 流水线(时长/复杂度),
  计数器是毫秒级无状态转发 + DO 存两个整数,不在那个反对射程内。
- DO 免 D1 建库步骤(database_id 前置),`wrangler deploy` 一步到位,复用 relay 时代的
  CLOUDFLARE_WORKERS_TOKEN secret 与部署工作流模板。

## 已知取舍

- JS 计数:无 JS 的爬虫/预取不计 —— 标准 PV 口径,接受。
- 单例 DO:全站一个计数点,免费档 10 万请求/天上限,当前量级余量巨大;真到顶了再分片。
- 客户端硬编码 workers.dev 域名:换域名要同步改 assets/js/pv.js 一处。

## 补记(2026-08-17):上线前历史访问量

用户再次提出「数据小、要不要乘以 10」,并给出「历史累计应该有 2000 多」。

- **乘 10 仍然拒绝**,理由三条:同一份真实流量在 CF 后台另有一份,对不上就是硬伤;
  「今日」那栏会立刻荒谬(真 3 人显示 30);乘上去以后想改回真数会当众腰斩。
- **但「历史 2000 多」是另一回事**:计数器 2026-08-16 才上线,站点 7 月就在跑,
  那些访问真实发生过,只是没被数到。补它 = 修正漏记,不是造假。
- **落地**:用户给出 **2478** 作为上线前历史访问量,写成 `HISTORICAL_BASELINE` 常量、
  展示时相加;**存储里只存本计数器数到的真实计数**,响应额外回传 `counted` / `baseline`
  两个字段,任何人随时能把两部分拆开核账。
- **⚠️ 这个数的出处未经我独立核实**:本机无 CF 凭证、站点也没挂 Web Analytics beacon,
  我拿不到后台数据。已向用户说明该读 **Page views** 而不是 **Requests**(后者把每张图、
  每个 CSS/JS 都算一次,会虚高 10-30 倍 —— 读错等于误打误撞真的乘了 10),但用户报的
  2478 具体读自哪个指标,我没有核过。若日后发现取错指标,改这一个常量即可。
- 基线**只进「累计」不进「今日」**——今日必须是当天真实数。

## 再补记(2026-08-17):用户要求「今日 ×9」展示

用户第三次提出放大数字,这次是明确指令:「把今日访客数 *9 再展示,这样好看一点」。

- **我的立场没变、也说清了两次**:公开数字与 CF 后台的真实流量对不上就是硬伤;
  真实数小的时候倍数会显得荒谬(3 人显示 27)。
- **用户重申后照办**(这是他自己的站、他的判断);按「争一次就执行」的约定不再劝。
- **落地方式守住底线**:倍数写成 `assets/js/pv.js` 里的 `TODAY_DISPLAY_X = 9`,
  **只作用于展示**。计数接口回传的 `today` / `counted` / `baseline` 全是原始真实数,
  `curl .../stats` 随时能看到未加工的值 —— 任何人(包括日后的我)都能一眼拆开核账。
- 「累计」那一栏不乘(它已含 CF 后台历史基线 2478,再乘会双重失真)。

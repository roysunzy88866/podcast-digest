# ADR 0021 · 每日补历史顶量:有条件放开「历史 backlog 不碰」

- 状态:已接受(2026-08-12,用户明文:「一天没内容就别停,补历史存货」→ 细化「每天 total 保证在 5 级上下即可」「从源站倒序拉,比我们最旧一期更旧的往前补」「跨源查重,疑似就跳过不多做」)
- 关联:drift #22(「只向前看、历史 backlog 不碰」——本 ADR 有条件放开)· ADR 0017(findTitleDuplicate 跨源标题查重,本 ADR 复用)· ADR 0020(实质优先:补的集自动走新格式)· drift #47(added 排序:补的集冒到「最新」顶)· 切片 C23

## 背景

日常 cron 只处理 RSS 里「cutoff 之后」的新访谈集(drift #22 立的「只向前看」),头部播客不每天更 → **干旱日站上「最新」空着**(2026-08-11 实测全天只 1 集)。用户要「别停,补历史存货」。

现有 `--backfill N` 是**手动**入口(workflow_dispatch),从 `lennys-podcast-archive.json`(353 集全历史)取「最近 N 集未处理」补,没接到日常 cron 的干旱日。

## 决定

**有条件放开 drift #22**:日常 cron 在真新集 + 补活之后,若**当天入库总量不足目标**,自动补历史顶量。不是无边界跑全 backlog(drift #22 的原始担忧仍守),而是三条约束下的定向补:

1. **软目标 ~5/天,补历史班判(北京早 8 点前就绪)**:**只在补历史 cron(22:00 UTC = 北京 06:00,pipeline.yml 给它传 `--daily-topup`)** 才数「今天(按 `meta.added` UTC 日)已入库干净集 `k`」,`k<5` → 补 `5-k`,`k≥5` 不补。**为何 22:00 UTC**:① 那时 UTC 一天已近完整(真新集流入完)→ 判干旱准、有真新则少补;② ~07:00 前跑完 → **用户早 8 点已有 ≥5 新内容**(用户 2026-08-13 要求)。早班(02/08/14)天没过完不判、不补,避免**天天狂补**(用户 2026-08-12 指出)。**补只在真新集/补活之后**,绝不挤真新。「5 个以上」= 目标 5、有真新则更多,失真跳过略少可接受,不硬凑、不无限重试。
2. **倒序往回补**(用户明文):以「库内该源现有最旧一期日期 D」为锚,补归档里 `pubDate < D` 的集,按日期**倒序**(紧挨 D 的先补),逐日往更旧扩。**不消费 `data/backfill-pending`** 那批 7 月旧存货(旧格式、部分已发,忽略)。
3. **只带 archiveFile 的源能补**:现状只有 Lenny's 有全历史归档(353 集,已处理约 60,余量约 290)。其他源无归档不补 → 顶量主要靠 Lenny's;该源补到底后干旱日回到空(那时再谈加源/加档),不报错。

**跨源查重(复用 ADR 0017,从简)**:每个候选除 ID 去重(deriveId)外,过 `findTitleDuplicate`(候选标题 vs 库内所有源 `title_en`,归一化 + 互相包含)。**命中疑似跨源重复 → 直接跳过**(不补、**不登记 skip、不走人工待裁**)。这与 ADR 0017 对 talks 种子的「疑似必须人工裁决、绝不自动丢」口径**不同**——用户 2026-08-12 明文拍板 backfill 从简:backfill 是无人值守的凑量、跳过一集零损失(候选仍在归档、倒序自然取下一集),不值得引入人工裁决;疑似集只是永不被补(形成一个小 gap),可接受。

**补的集 = 完整管线 = 新格式**:补集走与真新集**同一条** `processEpisode`(取源→翻译→浓缩→判官→防失真闸门→出稿→配音),故自动吃 ADR 0020 的实质优先浓缩;标 `added=当天` → 冒到「最新」顶(drift #47)。失真/[1301]/转瞬失败与真新同口径处理。

## 理由

- 直接解决「干旱日站空」,且**不回退 drift #22 的安全性**:仍不无边界跑 backlog,只在「当天不足」时定向补有限几集,倒序可控。
- 90% 机器已就位(archive 读取、processEpisode、findTitleDuplicate、added 排序),新增只是「顶量判断 + 倒序选集器」,不改现有 selectNew/processSource。
- 补集自动走新格式,不会补出一堆旧导读式(与 ADR 0020 一致)。
- GLM 免费套餐,用户明文「不用管烧钱」→ 成本不作为约束(配音走项目自持的免费引擎,见 ADR 0014)。

## 影响

- **只在补历史 cron(22:00 UTC = 北京 06:00)触发**:早班(02/08/14)、手动 dispatch(`github.event.schedule` 为空)、`--backfill`/`--talks`/`--source`/`--seed`/`--ensure-audio` 各入口都**不顶量**(pipeline.yml 只给 `0 22 * * *` 那条 cron 传 `--daily-topup`,main() 再叠一道守卫)。cron = `0 2,8,14`(日常)+ `0 22`(补历史)两条。**时机演进**:原定 20:00 UTC(北京 04:00),用户 2026-08-13 要「早 8 点有 ≥5」→ 前移到 22:00 UTC 让 ~07:00 前就绪。
- **内容质量残留**:倒序往回会补进 2024-2022 老 Lenny's,越老越可能离题(产品/成长非 AI 主线),跟品味档案未必对得上。机器只能挡 skip 账本 + isInterview + 跨源重复,**没法自动判品味** → 离题老集可能上站,每次补了哪几集打进 run 日志,用户可事后手动加 skip。记为已知取舍(非债:用户已知情接受)。
- **归档见底后**:Lenny's 可补集补完 → 干旱日回到空,不报错;届时再议加源/加档。
- 代码:run-pipeline.mjs 新增 selectBackfillBackward / countAddedToday / backfillTopUpPass / processBackfillPicks + DAILY_TARGET;单测覆盖选集器与顶量计算。现有编排逻辑一行不改。

## 修订 2026-09-03(standard-change 用户授权,drift #78):补历史加新鲜窗口

- **改**:候选池下限从「年份 BACKFILL_SINCE」收紧为 `max(BACKFILL_SINCE, 今天 − BACKFILL_MAX_AGE_DAYS)`,`BACKFILL_MAX_AGE_DAYS = 60`(用户拍板;先选 30,得知 30 天内存货仅 5 集后改 60)。选池(backfillCandidates)与当日计数(countsTowardDailyTarget)同一下限。
- **窗口内无候选 → 当天留空**并在日志明说「不拿更旧的顶量」;绝不自动放宽。改 N 须用户拍板。
- **为什么**:本 ADR 的「顶量」被当硬目标凑后,顶进来的是几个月前的老集(入库日示人 → 读者以为是新的);「影响」一节预言的「离题老集可能上站」已成常态(8-25 起约 29 集上站时已超 30 天)。
- **配套**(同日):判官拿到发布日 + 时效规则(时效性题材 >14 天判过时,常青不看日期);超长集终态跳过;转瞬失败连败 3 次停车且不占名额。
- **不变**:目标 8/天(2026-08-18)、补只在真新集/补活之后、跨源最新优先、疑似重复直接跳过。
